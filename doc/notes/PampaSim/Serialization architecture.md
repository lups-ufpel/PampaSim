I'm stumped on how to best write the serialization code. I've tried to tack on proper XML marshalling/unmarshalling thru JAXB well after we settled our own ad-hoc spec definition lang, and the cruft from that experiment lives on in the abstractions and interfaces that expect a specific data layout, e.g. the whole Spec class.

I quite like the idea of using the schema-to-java tool that JAXB provides, `xjc`. The issue is, I'd like to keep the XML data classes/objects "in the loop" as it were, so we don't even have to think about a parallel, actually serialized object when want to operate on the loaded simulation spec. I'd like a transparent abstraction for once! I want to guarantee synchronization between what we are working with and what will get saved to disk.

I can't/am not willing to monkey patch the autogenerated code, so that leaves me with maybe extending the XML Spec class to keep track of the additional, derived data structures that the runtime needs, which I find rather brittle. I'd need to define a custom JAXB `ObjectFactory` for the simulator package that would delegate most of the implementation to the usual generated ObjectFactory which would need to be stuffed somewhere else as I don't know how else to prevent the name conflict...

I'm working towards keeping track of that synchronization inside the refactored proper runtime Spec class. It's a decidedly less elegant, compromised solution. The lesser of the evils. It encapsulates the serializable object, and provides methods to store/load from files directly. For outside observers, it's as if the object itself is serializable, just as long as we are extra careful to not break the synchronization invariants when writing the Spec methods.

Immediate issues: the core Event interface doesn't deal with serialization. It shouldn't, really: most events are not trivially serializable, since they may reference objects that only get instantiated during execution like the Process event group does. Besides, we only want to store a small subset of all events. Only the External event group, matter of fact. Writing this bit down made me realize we already have the events which should be serializable enumerated in the simulation specification. Right. I can make the event code generator take an optional flag to make the generated event classes implement a serialization interface. That seems reasonable. The flag will apply over a whole event group, to take advantage of the existing External event group. Event groups bundle events that carry the same payload together, that's why they were created. The External group currently carries `ProcessCreationData` objects which I'd like oh so very much to simplify to the exact same class as the one that is currently generated from the XML schemas, one `ProcessCreationDataPayload`. It had to have the ugly suffix added to the end to disambiguate from the existing one, but I *think* there's a way to go without the original class, just as long as I figure out how to make the `creationId`s make sense.
The `creationId`s came to be when we needed a "foreign key" of sorts to link `ProcessViewModel`s (PVMs) to their actual `Process` objects, since PIDs aren't defined for every possible simulation tick, they are only defined after the process's been created. As of today (2026-04-15 hash faf661865eb) the `creationId`s are generated using a static monotonic counter:
```java
public static class CreationData {
		private static long idCounter = 0;
		private final long creationId = idCounter++;
		...
}
```
This way we got total ordering as a convenient little extra, unlike UUIDs.

So: how the hell are we meant to serialize this in a way that doesn't break everything? The solution must be able to reconstruct the same experiment exactly, or at the very least give the same results as the original. As it is written above, every new instance of CreationData increments the counter, and we can't retcon the static counter from outside if we were to somehow modify the `creationId` after initialization to try and reinstate eventual consistency manually. Bummer. I'd be even more bummed if this is the overarching pattern across all the payload types, add a little dynamism and the whole thing falls apart. I could do away with the identifier by just comparing references directly, but I fear for the performance hits. Can I use references as keys to a Map? [Turns out you can](https://stackoverflow.com/a/5797387)! This changes things. That means we can do the whole `creationId` associative map from PVMs to `Processes` without needing to change the class internals at all, we just sacrifice the ordering property. Hope we don't need it! We kinda do. The edge case has come up before. Consider two or more processes arriving at the same tick and how the different scheduling algorithms handle those simultaneous arrivals. Most of the ones I implemented end up reflecting the order they are processed, aka their order in the inbound event queue! Our old format implicitly encoded that through line ordering... Which is still possible to be fair, it's just clunky. Subdividing the ticks is just as bad. Making it so only one arrival happens per tick is also unrealistic. We must be able to encode intra-tick ordering somehow. Out of these options, the least offensive is subdividing the ticks... Store a ordering number that is used exclusively for the ordering inside a contended tick. That would fix some issues with the process editing too.
